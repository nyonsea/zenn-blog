## この記事の位置づけ

ある企業がAWS Organizationsで12の本番アカウントを運用しているという想定で、次の4点を満たすセキュリティ基盤の設計を検証した。

1. 本番アカウント全体にわたり、不審なAPI呼び出しや普段と異なる通信を継続して見つけ出す
2. 見つかった事象に対し、担当者の操作を挟まずに封じ込めの処理を走らせる
3. 重大度の高い検出が出たときにAmazon SNSへ通知する
4. 検出結果をすべてセキュリティ運用アカウントへ集める

12アカウント規模を個人の検証環境でそのまま再現するのは非現実的なので、今回は**Organizations配下の3アカウント構成**で、仕組みの核心部分(検知の集約・クロスアカウントの自動封じ込め・通知)を実機検証した。12アカウント特有の論点(展開の自動化、OU単位のSCP、Findingsのチューニングなど)は「本番環境ならどう改善するか」として別途整理する。

構築・検証の詳細(CLIコマンド、実際のログ、失敗例、スクリーンショット)は別記事([構築・検証編](#))にまとめている。この記事では、何をどう組むかという設計判断に絞って書く。

## 前提知識の整理

本題に入る前に、この記事で頻出する用語を簡単に整理しておく。既に知っている場合は読み飛ばしてよい。

- **AWS Organizations**: 複数のAWSアカウントを1つの組織としてまとめて管理する仕組み。組織には必ず1つの「管理アカウント」があり、その配下に「メンバーアカウント」がぶら下がる
- **委任管理者(delegated administrator)**: GuardDutyやSecurity Hubなど一部のAWSサービスには、Organizationsの管理アカウントとは別に、そのサービスの管理権限だけを委任できる仕組みがある。委任された先のアカウントを委任管理者と呼ぶ
- **AssumeRole**: あるIAMエンティティ(ユーザーやロール)が、一時的に別のIAMロールの権限を借りる操作。クロスアカウントでリソースを操作する際の基本的な仕組み
- **SCP(Service Control Policy)**: Organizations配下のアカウントに対して、どのAWSサービス・操作を許可/禁止するかを組織単位で制御するポリシー

## 全体構成

- **Account A(111111111111)**: Organizations管理アカウント。GuardDutyのメンバーにも委任管理者にもしない
- **Account B(222222222222)**: GuardDuty委任管理者 兼 セキュリティ運用アカウント
- **Account C(333333333333)**: GuardDutyメンバー 兼 本番アカウント役(Findingを発生させ、封じ込めの対象になる)

```
[Account C: 本番役]
  └─ GuardDuty Finding発生
       ↓ (自動集約、追加のクロスアカウント許可設定なし)
[Account B: セキュリティ運用]
  ├─ GuardDuty(委任管理者、Cのメンバー含めて閲覧)
  ├─ EventBridge(Findingを捕捉、severity>=7でフィルタ)
  ├─ Lambda(AssumeRoleでC側を操作、封じ込め実行)
  └─ SNS(重大度High/Critical通知)

[Account A: 管理アカウント]
  └─ 委任管理者の登録操作にのみ関与。監視・封じ込め対象には含めない
```

要件と、それを満たす仕組みの対応関係は以下の通り。

| 要件 | 満たす仕組み |
|---|---|
| 1. 不審なAPI呼び出し・通信の継続的な検出 | Account CでGuardDutyを有効化 |
| 2. 担当者の操作を挟まない封じ込め | EventBridgeでFindingを捕捉し、Lambdaを自動起動 |
| 3. 重大度の高い検出でSNS通知 | EventBridgeのイベントパターンでseverityフィルタ、Lambda内からSNS Publish |
| 4. 検出結果の集約 | GuardDutyの委任管理者機能でAccount Bに自動集約 |

## この記事で使うたとえ

クロスアカウントのIAMは、アカウントIDとロール名が並ぶだけの説明になりやすく、どの主体が何を許可されているのかが追いにくい。以下では、1棟のオフィスビルにたとえて説明する箇所がある。対応はこうしている。

| 構成要素 | たとえ |
|---|---|
| AWS Organizations | 1棟のオフィスビル |
| Account A(管理アカウント) | ビルの所有者・管理会社 |
| Account B(委任管理者・セキュリティ運用) | 常駐を委託された警備会社の防災センター |
| Account C(本番アカウント役) | 入居しているテナント企業のフロア |
| GuardDuty | 各フロアに設置されたセンサー |
| 委任管理者機能 | 全フロアのセンサーが防災センターに集まる配線 |
| EventBridge | 防災センターの警報受信盤。どの警報で誰を動かすかを決める |
| Lambda | 警報を受けて現場に向かう警備員 |
| 信頼ポリシー | 入館ゲートの通行許可 |
| 権限ポリシー | 入館後にしてよい作業の指示書 |
| `sts:ExternalId` | ゲートで提示する合言葉 |
| SNS | 管理会社とテナントへの連絡 |

このたとえが崩れる箇所もあるので、先に書いておく。IAMロールは「警備会社の社員」のような常設の存在ではなく、AssumeRoleのたびに有効期限つきで発行される通行証に近い。実際、今回の検証でもSTSの一時認証情報が期限切れになって作業が止まった場面があった(構築・検証編に記載)。オンプレミスのADアカウントのように「一度作ればそこに居続ける」ものではない、という点はこのたとえでは表現できない。

## 設計判断1: なぜ管理アカウントを監視対象に含めないのか

最初に組んだ構成(以下v2と呼ぶ)は、アカウント数を切り詰めるため2アカウントで試した。この構成では管理アカウント(Account A)自身をGuardDutyのメンバーにし、封じ込めLambdaのAssumeRole対象(つまり自動操作される側)にしていた。動作はするが、これには明確な弱点がある。

Organizationsの管理アカウントは、SCPの適用範囲やOrganizations全体の統制など、他のメンバーアカウントにはない特別な位置づけを持つ。ここに「担当者の操作を介さない自動封じ込め」の対象を含めるのは、最小権限・職務分離の観点から避けるべき設計だと考えた。もし封じ込めロジックにバグがあったり、誤って重大度の高いFindingが管理アカウント側で発生した場合、組織全体の統制に関わるアカウントに対して、人の承認なしに操作が走ってしまうことになる。

ビルのたとえで言えば、火災報知器が鳴ったら自動でシャッターを降ろす対象に、防災センターと管理会社のオフィスまで含めるか、という話になる。そこが閉じてしまうと、復旧の指揮を執る場所そのものが使えなくなる。

そこで3アカウント目(Account C)を追加し、管理アカウント(A)を完全に監視・封じ込め対象から外し、封じ込めの実行対象は本番アカウント役(C)だけに限定した(以下v3と呼ぶ)。この記事、および構築・検証編で扱っているのはこのv3構成である。

> オンプレミス環境で例えるなら、ドメインコントローラやAD管理端末を、一般業務端末と同じEDRの自動隔離ポリシーの対象に含めるかどうか、という論点に近い。管理基盤そのものは、通常の自動対応ルールの対象から意図的に外すのが一般的な設計だと考えている。管理端末が誤って隔離されると、復旧作業そのものに管理端末が使えなくなるという本末転倒が起きうる。今回のAWS構成でも同様に、管理アカウントが誤って封じ込め対象になると、Organizations全体の統制に影響が及ぶ可能性がある。

## 設計判断2: 委任管理者はどのアカウントに置くべきか

AWSの一般的なガイダンスでは、GuardDutyの委任管理者をOrganizationsの管理アカウント自身にすることは推奨されていない。理由は最小権限の原則で、管理アカウントにはセキュリティサービスの管理権限以外を極力持たせないほうが、影響範囲を限定できるためだ。

一方、管理アカウント自体をGuardDutyの「メンバー」として組み込むことは正式にサポートされた構成であり、条件は事前にそのアカウントでGuardDutyを有効化しておくことだけだった(構築・検証編で実機確認済み)。

この整理に従い、今回はAccount B(管理アカウントではない、新規作成した専用アカウント)を委任管理者に据えた。結果として、以下のような役割分担になった。

| アカウント | Organizations上の役割 | GuardDuty上の役割 |
|---|---|---|
| Account A | 管理アカウント | 関与なし(委任管理者の登録操作のみ) |
| Account B | メンバーアカウント | 委任管理者(セキュリティ運用) |
| Account C | メンバーアカウント | メンバー(監視・封じ込め対象) |

「Organizations上の管理者」と「GuardDutyというサービスの管理者」を分離して考えるのがポイントだった。Organizations全体の管理者はAccount Aのままで変わらないが、GuardDutyというサービスの文脈では、Account Bが実質的な管理者としてふるまう。

ビルの所有者が警備の詰所まで兼ねている状態を想像すると、この分離の意味が分かりやすい。鍵も監視機材も判断の権限も所有者1か所に集まるので、平常時は確かに手間が少ない。ただし所有者側で何か起きたとき、切り離して調べる相手がいない。所有と警備実務を別の主体に分けておくと、どちらか一方の不具合をもう一方から確認できる。

## 設計判断3: クロスアカウントIAMの2段階信頼構造

封じ込めLambdaはAccount B側に置き、Account C側のリソース(IAMアクセスキー)を操作する。これを安全に行うための信頼関係は、実は2段階になっている。

1. **Lambdaサービス → Account Bのロール**: AWS LambdaというサービスがAccount B内のロール(`GuardDutyContainmentLambdaRole`)を引き受けられるようにする信頼ポリシー。これはLambda関数が起動するために必ず必要な、いわば「実行契約」
2. **Account Bのロール → Account Cのロール**: Account C側のロール(`SecurityOpsContainmentRole`)が、Account Bの特定のロール(Lambdaの実行ロール)だけを信頼してAssumeRoleを許可する信頼ポリシー

この2つを1つのポリシーにまとめることはできない。もしAccount C側の信頼ポリシーに「Lambdaサービスなら誰でも」という条件を書いてしまうと、Account B以外の第三者が勝手に立てたLambdaからも、Account Cのロールを乗っ取れることになってしまう。信頼の起点(サービスを実行する主体)と、信頼の対象(特定のアカウントの特定のロール)を分けて管理する必要がある。

たとえるなら、これはAccount Cのフロアの入館管理にあたる。

- **信頼ポリシー(Trust Policy)= 入館ゲートの認証ルール**: 「どの警備会社のスタッフなら、このゲートを通っていいか」を決める。今回で言えば「Account Bの`GuardDutyContainmentLambdaRole`という名札を持つ人だけ、ゲートを通っていい」というルール
- **権限ポリシー(Permission Policy)= 入館後の行動ルール**: ゲートを通った後、「具体的に何をしていいか」を決める。今回は「特定の1ユーザーのアクセスキーを無効化する権限だけ」に絞っている

ゲートを通れたからといって、フロア内で何をしてもいいわけではない。この2つが揃って初めて、防災センターから派遣された警備員(Account BのLambda)が、Account Cのフロアに入り、指示書に書かれた作業だけを行える、という一連の動作が成立する。

加えて、Account C側の信頼ポリシーには`sts:ExternalId`を条件として設定した。これは、名札(Principal)が正しくても、合言葉を一緒に提示しないとゲートが開かない、という追加の防御にあたる。今回は同一の所有者が管理する2アカウント間の話なので必須ではないが、将来的に外部のセキュリティベンダーに監視・対応を委託するような構成に発展した場合、この合言葉がないと「別の顧客のふりをして誤って侵入する」という事故(confused deputy問題)を防げない。今のうちから習慣化しておく意図で組み込んだ。

> オンプレミスのADで言えば、委任(delegation)の範囲をOU単位・グループ単位で細かく絞るのと同じ考え方だと捉えている。「管理者なら誰でも」ではなく「この管理グループの、このメンバーだけ」に絞るのが基本という点は、AWSでもオンプレでも変わらない。

## 設計判断4: 封じ込め権限は最小限に絞る

封じ込めLambdaに与えたIAM権限は、意図的に極めて狭く設計した。

```json
{
  "Effect": "Allow",
  "Action": ["iam:UpdateAccessKey", "iam:ListAccessKeys"],
  "Resource": "arn:aws:iam::333333333333:user/<特定のテストユーザー>"
}
```

Resourceをワイルドカード(`user/*`)にせず、特定の1ユーザーに絞った。理由は、自動封じ込めが対象を誤って作動した場合の影響範囲(ブラストラディウス)を最小化するためだ。もしこの権限をアカウント内の全IAMユーザーに対して持たせてしまうと、誤検知や想定外の入力によって、無関係なユーザーのアクセスキーまで無効化してしまうリスクが生まれる。

派遣する警備員に、全フロアのマスターキーを渡すか、対象の1室の鍵だけを渡すかの違いになる。マスターキーのほうが「どの部屋で何が起きても対応できる」ので運用は確実に楽だ。ただし判断を誤ったときに、被害の止まる場所がどこにもなくなる。

これは検証中に実際に効果を発揮した。GuardDutyのサンプル検出結果機能は、実在しないダミーのユーザー名(`GeneratedFindingUserName`)を含むイベントを生成する仕様だった。この最小権限ポリシーのおかげで、Lambdaはダミーユーザーへの操作を`AccessDenied`で拒否した。バグではなく、設計通りに権限が機能した結果だ。詳細は構築・検証編に記載している。

本番の12アカウント運用であれば、`Resource`をワイルドカードにせざるを得ない場面も出てくるだろう(封じ込め対象のユーザーは検知するまで分からないため)。その場合は、以下のような代替の防御線を重ねることになる。

- 封じ込めアクション自体を「無効化」のような可逆的な操作に限定し、「削除」のような不可逆操作は含めない
- 誤検知が多いFindingタイプは自動対応の対象から除外し、人の承認を挟む
- CloudTrailで封じ込めLambdaの実行履歴を監視し、異常な頻度で操作が発生していないかアラートする

1つ目の「可逆的な操作に限定する」は、カードキーを一時停止するのと、ドアを溶接してしまうのとの違いにあたる。マスターキーを渡さざるを得ないなら、少なくとも取れる行動のほうを元に戻せる範囲に限っておく。

## AWSサービス選定の理由

| サービス | 採用理由 |
|---|---|
| GuardDuty | マネージド型の脅威検知。CloudTrail・VPC Flow Logs・DNSログを横断して分析するため、個別にログ基盤を構築する必要がない |
| Organizations + 委任管理者機能 | マルチアカウントでの検出結果集約を、カスタムのログ転送基盤なしで実現できる |
| EventBridge | GuardDuty Findingが委任管理者アカウントのデフォルトイベントバスに自動集約される仕様を利用し、追加のクロスアカウント許可設定なしでイベント駆動の対応を組める |
| Lambda | 軽量な封じ込めロジックをサーバーレスで実行。常時稼働のインスタンスを持たずに済む |
| SNS | 重大度の高い検出のみを人間にエスカレーションするための、シンプルな通知経路 |

いずれも、追加のインフラ(専用のログ収集サーバーや、常時稼働のジョブスケジューラなど)を持たずに構成できる点を重視して選んだ。個人の検証環境でコストをかけずに試せる、という制約とも相性がよかった。

## 従来のセキュリティ運用との接続

自治体・企業でのSOC運用、EDR・SIEM(CrowdStrike、Exabeamなど)を扱ってきた経験から見ると、この構成は「検知」「判断」「対応」「報告」という従来のSOC運用フローを、AWSのマネージドサービスに置き換えたものと捉えられる。

- 検知: EDR/SIEMでの異常検知 → GuardDutyでの異常API呼び出し検知
- 判断: SOCアナリストによるトリアージ → EventBridgeのイベントパターンによる重大度フィルタ
- 対応: 手動での端末隔離・アカウント無効化 → Lambdaによる自動封じ込め
- 報告: インシデントチケット起票 → SNS通知

従来のSOC運用と大きく異なるのは、「対応」が人の判断を介さず自動化されている点だ。これは要件2(担当者の操作を挟まない)を満たす一方で、誤検知時の影響範囲をどう制限するかという新しい設計課題を生む。今回、封じ込め権限を1ユーザーに絞ったのは、この課題への対応でもある。

また、オンプレミスのAD管理と比較すると、権限管理の考え方にも共通点がある。ADで言う「委任(delegation)」の範囲をOU単位で絞る発想は、IAMロールの信頼ポリシーで特定のロールだけを信頼先に指定する発想と本質的に同じだ。認証(誰であるかの確認)と認可(何をしていいかの確認)を分けて考える、という基本原則もAWSとオンプレで変わらない。

## 本番(12アカウント)ならどう改善するか

今回の3アカウント構成で検証したのは、あくまで仕組みの核心部分だ。12アカウント規模で実際に運用するなら、以下を追加で検討する必要がある。

### 展開の自動化

今回はCLIで手動構築したが、12アカウント分を手作業で展開するのは非現実的。AWS Control TowerのカスタマイズやCloudFormation StackSetsによる自動展開が前提になる。特にIAMロール・EventBridgeルール・Lambda関数といったリソースは、全アカウントで同じ構成を維持する必要があるため、Infrastructure as Codeでの一元管理が実質的に必須になる。

### OU単位のSCP設計

本番用アカウントをまとめたOUに対するSCPは、今回の構成(フラットな3アカウント)では検証できていない。例えば、GuardDutyを無効化する操作自体をSCPで禁止しておけば、本番アカウント側でうっかりGuardDutyが止められてしまう事故を防げる。

### Findingsのチューニング

サンプルFindingsは数件〜数百件レベルで一括発生させられるが、実運用で発生する誤検知の量やアラート疲れの問題は、実際の運用データがないと分からない。severityによるフィルタだけでなく、Findingタイプごとのホワイトリスト・グレーリストを運用しながら育てていく必要があるだろう。

### 自動封じ込めのブラストラディウス制御

12の顧客向け本番アカウントで自動封じ込めが誤作動した場合の影響範囲は、机上の検討にとどまる。重大度や検出タイプに応じて、自動対応と人的承認を挟む対応を分けるといった段階的な設計が必要になる可能性がある。例えば、

- Critical severityのみ完全自動封じ込め
- High severityは封じ込め案を提示し、Slack等での承認を経て実行
- それ以外は通知のみ

といった多段階の対応フローを検討する余地がある。

## まとめ

3アカウント構成での検証を通じて、単に「GuardDutyを有効にしてLambdaで封じ込める」という表面的な理解では見えてこない設計判断がいくつかあった。特に、管理アカウントを監視対象から外す判断、クロスアカウントの2段階信頼構造、最小権限による誤検知時の影響範囲の限定は、AWSだけの経験では気づきにくい部分だと思う。

## この記事について

自宅Proxmox VE上に構築した検証環境で、オンプレミスAD（`nyondev.local`）とMicrosoft Entra ID（Azure無料アカウントで作成したテナント）をMicrosoft Entra Connectでハイブリッド接続する検証を行った。

構築自体は公式ドキュメント通りに進めれば数十分で終わるはずだったが、実際には性質の異なる3つの認証トラブルに順番にぶつかり、それぞれ原因の切り分けから対処まで丸一日を要した。特に2つ目のトラブル（`AADSTS50020`）は、Azure無料アカウントを個人のMicrosoftアカウント（MSA）で作成した場合に起こりやすい、二重アイデンティティの問題だった。

**本記事はすべて自宅検証環境での作業であり、実務での構築経験ではない。** その前提で読んでいただきたい。

---

## 1. 検証の目的

長年、自治体の情報システム部門とITエンジニアとしてWindows Server・Active Directory・VMware・セキュリティ運用に携わってきた。AWSの学習と並行して、オンプレADの知識がクラウドのID管理（Entra ID）にどう接続されるのかを実地で確認しておきたいと考え、今回の検証に至った。

具体的な検証目的は以下の3点。

- オンプレADのユーザーが、どのような形でEntra ID側に同期されるのか
- `.local`ドメインのような検証済みドメインを持たない環境で、UPN（ユーザープリンシパル名）がどう扱われるのか
- ハイブリッド構成特有の認証トラブルは、どこまで自力で切り分けられるのか

## 2. 環境構成

自宅Proxmox VE（ノード名: `pve2`）上に、企業ネットワークを模した環境を構築している。

![おうちクラウドネットワーク構成図](/images/00-network-diagram.png)
*BASTIONが唯一の踏み台としてNAT機能を持ち、内部LAN上のAZR01がLDAPでDC1を読み取り、HTTPS経由でMicrosoft Entra IDにプッシュする*

- **自宅LAN**（`192.168.11.0/24`）：ノートPCと、踏み台サーバー`BASTION`のWAN側インターフェースが存在する
- **内部LAN**（`192.168.100.0/24`）：`BASTION`のみが自宅LANと内部LANの両方に接続する「唯一の踏み台」で、内部LAN側の通信はすべて`BASTION`を経由する
- `BASTION`にはNAT機能を構成済みで、内部LAN側のサーバーは`BASTION`経由でインターネットへの**発信のみ**が可能

| ホスト名 | 役割 | OS | IP（内部LAN） |
|---|---|---|---|
| BASTION | 踏み台 + NAT | Windows Server 2022 | 192.168.100.1 |
| DC1 | ドメインコントローラー | Windows Server 2022 | 192.168.100.10 |
| DC2 | 追加ドメインコントローラー | Windows Server 2025 | 192.168.100.11 |
| AZR01 | Entra Connect用 | Windows Server 2025 | 192.168.100.21 |

ドメインは`nyondev.local`、フォレスト機能レベル・ドメイン機能レベルともにWindows Server 2016。DC1⇔DC2間のAD複製は事前に正常性を確認済み（`repadmin /showrepl`で5パーティション全て成功）。

## 3. UPN設計の判断

Entra Connectを構成する前に、UPN（ユーザープリンシパル名）の扱いを決めておく必要があった。

オンプレADのUPNサフィックスは`nyondev.local`だが、これは**インターネット上で検証済みドメインとしてMicrosoft Entra IDに登録できない**（`.local`はICANNの正式なTLDではないため）。この制約は、オンプレADの設計では意識することのなかった、クラウド連携特有の考慮点だった。

選択肢は大きく2つある。

- **A案（採用）**：UPNサフィックスの不一致を許容し、Entra ID側では自動的にテナントの既定ドメイン（`hogehoge99gmail.onmicrosoft.com`）にフォールバックさせる
- **B案（不採用）**：独自ドメインを取得し、Entra IDの検証済みドメインとして登録した上で、オンプレADのUPNサフィックスもそのドメインに揃える

今回は独自ドメインを保有していないこと、また検証の主目的が「UPNフォールバックが実際にどう見えるか」を確認することだったため、A案で進めることにした。実務でハイブリッド構成を設計する場合は、社内ドメインを検証済みドメインとして登録するB案が基本になるはずだが、その場合でも「フォールバックが発生した場合にどう見えるか」を事前に把握しておく価値はあると考えている。

## 4. 構築：Entra Connectのインストール

### バージョン確認

Entra管理センターの「作業の開始」画面には、以下の警告が表示されていた。

> **対応が必要です**：Microsoftは、2026年9月30日をもって、2.5.79.0より前のバージョンのMicrosoft Entra Connectを廃止します。

ダウンロードした`AzureADConnect.msi`のプロパティを確認したところ、バージョンは`2.6.84.0`（2026年7月ビルド）であり、廃止基準を満たしていることを確認してから作業を開始した。バージョンを確認せずに古いインストーラーを使い始めると、構築の後半で作業をやり直す羽目になりかねないので、この確認は最初に済ませておくべき手順だと感じた。

![インストーラーのプロパティでバージョンを確認](/images/01-version-check.png)
*タグに `Installer, 2.6.84.0` と表示されており、廃止基準（2.5.79.0以降）を満たしていることを確認*

### ウィザードの進行

インストール自体は問題なく完了し、「簡単設定」の画面まで進んだ。ここで想定通り、以下の警告が表示された。

> `nyondev.local` は、ルーティング可能なドメインではありません。カスタム設定を使用して、ユーザーのサインイン オプションを構成することが推奨されます。

![簡単設定画面でのUPN警告](/images/02-upn-warning.png)

前述のA案を明示的に選択するため、「簡単設定」ではなく「カスタマイズ」を選んで進めた。

「ユーザー サインイン」の画面では、**パスワード ハッシュ同期（PHS）**を選択した。2026年現在の標準的な推奨方式であり、特殊なフェデレーション要件もないため、今回の検証目的には過不足のない選択だと判断した。シングルサインオンは、BASTIONまたはDC上への追加のコンピューターアカウント作成が必要になり構成が一段複雑になるため、今回は有効化していない。

![パスワードハッシュ同期を選択](/images/03-phs-selected.png)

## 5. トラブル①：IE ESCによる複数ドメインのブロック

「Microsoft Entra ID に接続する」の画面でサインインを試みたところ、Internet Explorerのセキュリティ強化の構成（IE ESC）によって、複数のMicrosoftドメインが順番にブロックされた。

- `login.microsoftonline.com`
- `aadcdn.msauth.net`
- `login.live.com`

Entra Connectのウィザードは内部的にIEエンジンを使用しており、Windows Server既定のIE ESCがこれを妨げる。1ドメインずつ「信頼済みサイト」に追加していけば通過はできるが、Microsoftのサインインフローは認証パターンによって複数ドメインを経由するため、この場当たり的な対応では埒が明かないことがある。

![IE ESCによるブロック（login.microsoftonline.com）](/images/04-ie-esc-block.png)

最終的に「サインインするには JavaScript が必要です」というエラーに突き当たった。これは信頼済みサイトへの追加だけでは解消しない、IE ESCのスクリプト実行制限に起因するものだった。

![JavaScriptが必要ですというエラー画面](/images/05-javascript-error.png)

ここでIEの閲覧履歴（Cookie・一時ファイル）を削除したところ、この問題は解消した。検証環境であればIE ESC自体を無効化してしまう方が早いが、今回は影響範囲を確認しながら進めたかったため、キャッシュクリアという最小限の対応にとどめた。

## 6. トラブル②：AADSTS50020 — MSAとテナント管理者の二重アイデンティティ

IE ESCの問題を越えても、サインインは次のエラーで止まった。

```
AADSTS50020: User account 'hogehoge99@gmail.com' from identity provider
'live.com' does not exist in tenant '' and cannot access the application
'cb1056e2-e479-49de-ae31-7812af012ed8'(Microsoft Azure Active Directory Connect)
in that tenant. The account needs to be added as an external user in that
tenant first. Sign out and sign in again with a different Azure Active
Directory user account.
```

![AADSTS50020エラー画面](/images/06-aadsts50020.png)

### ログの読み方

まずエラーメッセージの構造を分解して読んだ。着目したのは、上記メッセージ中の`tenant ''`という部分、つまり`does not exist in tenant ''`の`''`（空文字列）だった。実際に他のAADSTS50020の事例を確認すると、この位置には`'Microsoft Services'`（MSAの既定テナント名）のようなテナント名や、テナントのGUIDが入っているのが通常であり、ここが空になっているのは、認証要求がテナントに正しくルーティングされる前の段階で弾かれていることを示唆していた。

### 試して効かなかった対処

以下を順に試したが、いずれも同じエラーが再発した。

1. IEのキャッシュ・Cookieの再クリア
2. `AzureADConnect.exe /InteractiveAuth`スイッチによる、ウィザード内蔵のIE認証UIを経由しない起動方法への切り替え

`/InteractiveAuth`を試しても同じ結果だったことから、原因はブラウザーエンジンの問題ではなく、**アカウント自体の構造**にあると判断した。

### 根本原因の特定

Entra管理センターでユーザー一覧を確認したところ、`hogehoge99@gmail.com`のユーザープリンシパル名が以下の形式になっていることが分かった。

```
hogehoge99_gmail.com#EXT#@hogehoge99gmail.onmicrosoft.com
```

![Entra管理センターで確認したUPNの実態](/images/07-upn-ext-format.png)

「ユーザーの種類」は「メンバー」だったが、UPNの命名規則自体は外部（ゲスト/B2B）アカウント特有の`#EXT#`形式だった。Azure無料アカウントを個人のMicrosoftアカウント（MSA）で登録した場合、同じメールアドレスで「個人アカウント」と「テナントの職場アカウント」という**技術的に別の2つのアイデンティティ**が裏側に存在する状態になる。Entra Connectのサインイン画面に単に`hogehoge99@gmail.com`と入力すると、この2つのうちどちらに解決すべきかの判定に失敗し、個人アカウント（`identity provider 'live.com'`）側として扱われてテナントに到達できていなかった、というのが実態だった。

試しにこのフルUPN（`#EXT#`形式）をそのままウィザードのユーザー名欄に入力してみたが、通常のメールアドレス形式として無効と判定され、入力の時点で弾かれた。この方法は使えないことが分かった。

![#EXT#形式のUPNを直接入力するとバリデーションエラーになる](/images/08-ext-input-rejected.png)

### 解決策：専用のクラウド管理者アカウントを新規作成する

ここで、`hogehoge99@gmail.com`をそのまま使い続けるのではなく、**MSAと一切紐付かない、テナント内で完結したクラウドのみのグローバル管理者アカウント**を新規作成する方針に切り替えた。

1. Entra管理センターで新規ユーザーを作成（`syncadmin@hogehoge99gmail.onmicrosoft.com`）
2. 「グローバル管理者」ロールを割り当て
3. 初回サインインでパスワードを変更し、Microsoft Authenticatorアプリを使ったMFAを登録

![新規ユーザー作成のレビュー画面](/images/09-syncadmin-review.png)

![グローバル管理者ロールの割り当てが完了](/images/10-global-admin-assigned.png)

このアカウントでEntra Connectウィザードの「Microsoft Entra ID に接続する」画面から再度サインインしたところ、`AADSTS50020`は再発せず、「ディレクトリ スキーマの取得中」というプログレスバーが進み始めた。

![専用アカウントでの認証に成功し、ディレクトリスキーマの取得が進行](/images/11-directory-schema-success.png)

### 実務での教訓

Entra Connectの認証には、テナント管理者の個人アカウントを流用するのではなく、**専用のクラウドのみのサービスアカウントを用意する**のが一般的なプラクティスだと理解した。今回のようにMSAでテナントを作成した検証環境では特に踏みやすい罠だが、実務で独自ドメインの職場アカウントのみを使う環境であれば、この種の二重アイデンティティ問題自体が発生しない可能性が高い。裏を返せば、今回の問題は「Azure無料アカウントをMSAで作った検証環境特有の事情」であり、実務でそのまま遭遇するとは限らない点には注意したい。

## 7. トラブル③：アプリケーションベース認証の構成失敗

専用アカウントでの認証を突破し、オンプレAD側の接続（`NYONDEV\administrator`によるフォレストアカウントの新規作成）、UPNサインインの構成（A案のチェックボックス）、ドメイン/OUフィルタリング、ユーザー識別、フィルタリング、オプション機能（パスワード ハッシュ同期のみ選択）と、ウィザードを順調に進め、最終確認画面から「インストール」を実行した。

![UPNサフィックスの不一致を許容するA案のチェックボックス](/images/12-upn-fallback-checked.png)

ところが、構成の最終段階で以下のエラーが表示された。

> Microsoft Entra Connect で、このサーバーに対してアプリケーション ベースの認証を構成できませんでした。セットアップを続行できません。

![アプリケーションベースの認証が構成できないエラー](/images/13-abauth-error.png)

調べたところ、これは`2.6.84.0`のような比較的新しいバージョンで導入された仕様変更に起因するものだった。以前のバージョンでは、Microsoft Entra認証のセットアップに失敗した場合、ウィザードがレガシーの「ディレクトリ同期アカウント」方式へ自動的にフォールバックしていたが、現在のバージョンではこの自動フォールバックが行われなくなり、根本原因を解決できるようにエラーで停止する仕様に変わっている。

Microsoftの公式コミュニティでは、このエラーの原因として以下が挙げられていた。

- サーバーからMicrosoft Entra認証エンドポイントへの到達性の問題
- TLS 1.2 / Schannelの構成不備
- グローバル管理者アカウントの認証失敗
- 証明書登録の不一致
- 他のEntra Connectサーバーでの重複したアプリケーションベース認証構成

今回のケースでは、`syncadmin`アカウントを**数分前に作成し、グローバル管理者ロールを割り当てた直後**だったことが気になった。ロールの割り当てがMicrosoft Graph側の全エンドポイントに完全に反映されるまでには、多少のタイムラグが生じることがある。この仮説のもと、特別な追加対応はせず「再試行」をクリックしたところ、今度は処理が進行し、「シングル サインオンを構成しています」「Connect Health エージェント インストール中」と順調にステップが進み、最終的に「構成が完了しました」の画面に到達した。

![構成が完了しました](/images/14-config-complete.png)

厳密には、ロール伝播のタイムラグが原因だったのか、それとも単に一時的な通信エラーだったのかを完全に切り分けることはできていない。この点は「要確認」として、断定は避けたい。

## 8. 検証：オンプレADからEntra IDへの同期確認

構築が完了した後、実際にオンプレAD側で作成したユーザーがEntra ID側に反映されるかを確認した。

1. DC1の「Active Directory ユーザーとコンピューター」で、`Users`コンテナにテストユーザー（`Test Sync` / `testsync@nyondev.local`）を作成
2. AZR01で管理者権限のPowerShellを開き、差分同期を手動でトリガー

```powershell
Import-Module ADSync
Start-ADSyncSyncCycle -PolicyType Delta
```

```
Result
------
Success
```

![差分同期サイクルの実行結果](/images/15-sync-success.png)

3. Entra管理センターの「ユーザー」一覧を再読み込みし、`Test Sync`が表示されることを確認

同期後、Entra ID側でのユーザープリンシパル名は`testsync@hogehoge99gmail.onmicrosoft.com`となっており、「オンプレミスの...」列が「はい」と表示されていた。DC1側では`nyondev.local`サフィックスで作成したユーザーが、想定通りテナントの既定ドメインへフォールバックした形でEntra ID側に反映されることを、実際の画面上で確認できた。

![Entra ID側でTest Syncユーザーの同期を確認](/images/16-testsync-confirmed.png)

（構成図は「2. 環境構成」に掲載したものと同一のため、そちらを参照）

なお、Entra Connectは既定で30分ごとの自動同期を行うが、検証中はこのように`Start-ADSyncSyncCycle -PolicyType Delta`で任意のタイミングでの差分同期を実行できる。

### 同期の実際の向き：「DC1からのプッシュ」ではない

ここで、一見わかりにくい点を整理しておきたい。「DC1でユーザーを作成したら、その変更がAZR01経由でEntra IDに送られる」という表現は結果として正しいが、**実際に通信を能動的に開始しているのは常にAZR01側**であり、DC1やEntra IDが変更を能動的にプッシュしているわけではない。

1. **AZR01 → DC1**：同期サイクル（既定30分ごと、または今回のような手動トリガー）のたびに、AZR01上の同期エンジンが**LDAPでDC1（またはAD全体）へ接続しに行き**、USN（Update Sequence Number）を基準に前回同期時点からの差分を読み取る。DC1側から能動的に何かをAZR01へ送信することはない
2. **AZR01内部**：読み取った変更はAZR01内のコネクタスペースで処理され、メタバースに反映される
3. **AZR01 → Entra ID**：処理後、AZR01がMicrosoft Graph API経由（HTTPS）でEntra ID側に変更をプッシュする。この通信はBASTIONのNAT機能を経由してインターネットへ発信されている

つまり、DC1・Entra IDのどちらも「受け身」であり、両者の接続を仲介しているAZR01が唯一の能動的なプレイヤーということになる。この向きを理解しておくと、同期が反映されない場合のトラブルシューティングでも、「AZR01からDC1へのLDAP到達性」「AZR01からEntra IDへのHTTPS到達性」のどちらに問題があるのかを切り分けやすくなる。

## 9. 失敗点・制約

- 今回はIE ESCを個別ドメインの信頼済みサイト追加とキャッシュクリアで乗り切ったが、対症療法的な対応に終始してしまった。時間を区切って、早い段階でIE ESC自体の無効化に切り替える判断をした方が効率的だったと思う
- アプリケーションベース認証構成失敗の根本原因（ロール伝播のタイムラグか、それ以外か）を完全には特定できていない
- インストーラーはIEエンジンに依存した部分が残っており、Windows Serverの既定セキュリティ設定との相性の悪さは今回のような検証でも顕在化しやすい

## 10. 本番環境ならどう変えるか

- `.local`のような検証済みドメインにできないUPNサフィックスを使い続けるのではなく、独自ドメインをEntra IDの検証済みドメインとして登録し、UPNフォールバックが発生しない構成にする
- Entra Connectの認証には、最初から専用のクラウドのみのサービスアカウントを用意し、テナント管理者の個人アカウント（ましてやMSA由来のアカウント）を流用しない
- グローバル管理者ロールは常時付与のままにせず、構築作業完了後にPIM（Privileged Identity Management）などで必要な時だけ昇格する運用に切り替える。常時グローバル管理者権限を持つアカウントを放置するのは、最小権限の原則に反する
- 初回構築時は「ステージング モード」を有効にし、実際にAD/Entra ID双方へのエクスポートが走る前に、差分の内容を確認してから本番反映する

## 11. コスト・運用面

- 今回の検証はAzureの無料アカウントの範囲内で完結しており、追加コストは発生していない
- 実運用では、Entra Connect Health（今回のインストールでもエージェントが自動導入されている）を使った同期状態の監視や、同期エラー発生時のアラート運用を組み込む必要がある
- 同期対象ユーザー数が多い環境では、OU単位でのフィルタリングを行い、同期範囲を必要最小限に絞る設計も検討すべきだと感じた

## まとめ

オンプレADとMicrosoft Entra IDのハイブリッド接続は、手順としては公式ドキュメント通りに進めれば完了するはずのものだったが、実際には

1. Windows Server既定のセキュリティ設定（IE ESC）
2. Azure無料アカウント特有のMSAとテナント管理者の二重アイデンティティ
3. Entra Connectの新しいバージョンで変更された、アプリケーションベース認証のエラーハンドリング仕様

という、性質の異なる3種類のトラブルに順番に向き合うことになった。特に2つ目のトラブルは、エラーメッセージを字面通りに読むだけでなく、テナントのアカウント構造そのものを疑って確認しないと解決に辿り着けないものだった。
